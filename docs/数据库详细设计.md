# 数据库详细设计

## 1. 设计原则

1. 所有业务对象统一使用 `UUID` 作为主键，用户可读编号单独保存。
2. 标准、规则、执行器、模型和提示模板全部版本化，历史轮次只引用快照，不回写原记录。
3. 主任务只对应一个产品和一个型号；轮次是整改与复核的最小业务单元。
4. 标准与规则分开管理，动态标准审核项只在轮次快照内生成和保留。
5. 规则执行采用“逻辑执行 + 不可变尝试记录”模型，重试不覆盖原结果。
6. 核心字段稳定、任务级语义事实开放；产品专用技术参数不强行做全局字典化。
7. 所有表都保留 `created_at`、`updated_at`，需要审计的表再加 `created_by`、`updated_by`、`operation_reason`。
8. 删除优先采用状态归档和软删除，只有未发布草稿允许物理删除。

## 2. 通用字段约定

| 字段 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `code` | 人类可读编码，任务、标准、规则、执行器等实体建议保留 |
| `status` | 状态枚举 |
| `version_no` | 版本号，草稿可为空，发布后递增 |
| `snapshot_ref` | 本轮快照引用，通常存 UUID 或快照编码 |
| `created_at` / `updated_at` | UTC 时间戳 |
| `created_by` / `updated_by` | 操作人 UUID |
| `operation_reason` | 变更原因 |

#### `parsed_block`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | UUID | PK | 解析块主键 |
| `file_id` | UUID | FK -> task_file | 所属文件 |
| `page_no` | integer | 非空 | 页码 |
| `block_type` | varchar(32) | 非空 | 段落、表格、图片、标题栏等 |
| `content_text` | text | 可空 | 文本内容 |
| `bbox` | jsonb | 可空 | 坐标 |
| `confidence` | numeric(5,4) | 非空 | 置信度 |
| `source_ref` | varchar(128) | 可空 | 解析引擎来源 |

解析结果约定：

1. `parse_summary` 保存解析器、页数或工作表数、块数、字符数、重试次数、完成时间，以及 `needs_ocr`、空文本页和失败错误。
2. `source_ref` 使用稳定可读格式：PDF 为 `pdf:page:{page}:line:{line}`，Word 为 `docx:paragraph:{index}` 或 `docx:table:{table}:row:{row}`，Excel 为 `xlsx:{sheet}!{range}`。
3. 文件重新解析时在同一事务中删除该文件旧 `parsed_block` 并写入新块，避免不同解析版本混用。
4. `bbox` 仅在解析引擎能够给出可信版面坐标时写入。OCR 块使用 PDF 点坐标，原点位于页面左上角，并同时保存页面宽高和 `unit=pt`；文本层解析仍以页码和 `source_ref` 定位。
5. OCR 来源引用格式为 `ocr:{engine}:page:{page}:line:{line}`，`confidence` 归一化到 `0..1`。未识别页保存在 `parse_summary.unresolved_ocr_pages`，不得生成空证据块。
6. `parse_summary.page_assets` 保存页面资产元数据：`page_no`、`page_width`、`page_height`、`thumbnail_storage_key`、`is_drawing`、`detection_method` 和 `detection_confidence`。PNG 二进制只进入对象存储，不进入数据库 JSON。
7. 区域证据不单独复制为永久对象，使用原始 PDF 对 `bbox` 实时裁剪，避免大量临时图片和版本清理遗漏；需要长期保留时由问题证据或报告对象键显式固化。
8. `parse_summary.quality_metrics` 保存质量分、平均置信度、页面覆盖率、低置信块和未解析页统计；`review_required=true` 时不得无提示进入自动审核。
9. `parse_summary.quality_review` 保存 `pending / accepted / reparse / not_required` 状态、审核人、审核时间和原因；人工块修订次数保存在 `manual_revision_count`。
10. 人工修订直接更新当前解析块，同时使用 `operation_log` 的 `parsed_block.manual_revision` 记录不可变前后快照；重新解析仍按文件版本隔离并替换当前块集合。

## 5. 关键索引与约束

1. `audit_task.task_no`、`standard_version.full_code`、`rule_definition.rule_code`、`executor_definition.executor_code` 必须唯一。
2. `audit_round(task_id, round_no)`、`rule_version(rule_definition_id, version_no)`、`executor_version(executor_definition_id, version_no)` 必须唯一。
3. `task_file(task_id, sha256)` 需要联合索引，用于去重和复用解析结果。
4. 所有 `status` 字段都要建立普通索引，便于工作台筛选。
5. `issue_source`、`issue_evidence`、`execution_step` 建议保留外键索引，支持问题追溯和性能查询。

## 6. 数据一致性策略

1. 已发布标准版本、规则版本、执行器版本和报告不得原地修改。
2. 轮次一旦锁定快照，轮次内引用的标准、规则、模型、提示模板和文件版本不回写。
3. 规则执行失败重试只新增 `rule_execution_attempt`，不覆盖原尝试。
4. 轮次变更字段、文件、标准或覆盖参数时，先写 `rule_impact_analysis`，再由人工确认重跑。
5. 软删除记录仍保留审计链，物理删除只允许未发布草稿。

## 7. 首期实现顺序

1. 先落 `sys_user`、`auth_session`、`audit_task`、`audit_round`、`task_file`、`standard`、`standard_version`、`executor_definition`、`executor_version`、`rule_definition`、`rule_version`。
2. 再落 `round_standard`、`round_rule`、`dynamic_audit_item`、`audit_run`、`rule_execution`、`audit_issue`。
3. 最后补 `report`、`operation_log`、`model_config`、`queue_job`、`system_alert` 等支撑表。
